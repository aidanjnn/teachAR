## Useful differences found in source

1. **Native presentation still renders one selected hand.** `GhostPresentation` allocates 25 joints/24 bones and selects left *or* right; `GuideController` supplies `Targets[0]`. The reducer supports multiple active-hand targets, so its display can under-explain a two-hand movement. Port paired ghost rendering and live palm outlines before a two-hand demonstration. This is a concrete implementation gap, not a reason to replace the native reducer. [Ghost source](https://github.com/aidanjnn/trail/blob/2a0b91c/apps/quest/Assets/Trail/Presentation/GhostPresentation.cs), [guide display](https://github.com/aidanjnn/trail/blob/2a0b91c/apps/quest/Assets/Trail/Runtime/Guide/GuideController.cs).

2. **The native controls are engineering panels.** Capture exposes “Record 5 seconds”, “Record up to 120s / stop”, Sample mark and Mat moved. Storage separately exposes Upload, Refresh and Preload. Capture requires opposite-hand touch, 600 ms hold, then withdrawal; Guide/Storage trigger after dwell without that withdrawal. The interaction inconsistency and repeated panels will be confusing. Replace their presentation with one role-aware Create/Follow shell and contextual controls, while calling the existing controllers. Use actual visible button surfaces with matching hit targets. [Capture UI](https://github.com/aidanjnn/trail/blob/2a0b91c/apps/quest/Assets/Trail/Presentation/CaptureControlPanel.cs), [Storage UI](https://github.com/aidanjnn/trail/blob/2a0b91c/apps/quest/Assets/Trail/Runtime/Storage/StorageControlPanel.cs).

3. **Native capture lacks this one-time save zone and deliberate pause/resume.** `CaptureReplaySession` exposes StartRecording/StopRecording, while the local experiment has tutorial-scoped return-to-save, pause/resume, paired replay, integrated review and automatic local saving. Port the lifecycle and adversarial tests, not the browser state machine wholesale. [Capture session](https://github.com/aidanjnn/trail/blob/2a0b91c/apps/quest/Assets/Trail/Runtime/Record/CaptureReplaySession.cs).

4. **Native calibration is more rigorous and more constrained.** It fits three measured marks and independently checks a fourth, with 2 cm acceptance thresholds. The default declared workspace is 50 × 35 cm; loading requires the recording’s rectangular geometry. Our two-point placement accepts a new heading distance but cannot offer that held-out check. Keep native registration evidence. Explain it through a visual workspace setup, and introduce a separate explicitly approximate placement mode only if the product needs it; do not silently remove the fit checks. Both approaches preserve scale and neither automatically adapts to new object dimensions. [Calibration](https://github.com/aidanjnn/trail/blob/2a0b91c/apps/quest/Assets/Trail/Motion/WorkspaceCalibration.cs).

5. **Native cue progression is more developed, but precision/display need tuning.** The reducer separates cosmetic cue progress from actual gate completion, tracks fresh observations and attempts, and can continue after backend loss. Native defaults include 5 cm target tolerance / 6 cm gate tolerance; its displayed target ring has a fixed 2.5 cm radius. Those are code defaults, not accuracy measurements, and they can recreate the “abnormally precise” feeling. Display the actual reviewed tolerance volume and evaluate forgiving task-specific settings on Quest. Keep missing tracking neutral. [Matcher](https://github.com/aidanjnn/trail/blob/2a0b91c/apps/quest/Assets/Trail/Motion/GuideMatcher.cs), [definitions](https://github.com/aidanjnn/trail/blob/2a0b91c/apps/quest/Assets/Trail/Motion/GuideDefinition.cs).

6. **Motion segments are not invented task instructions.** Native authoring proposes boundaries from markers/pauses and requires reviewed instructions. Keep that generic boundary machinery; avoid hardcoded folding names. A save-zone event can supply an explicit reviewed boundary and exclude the return gesture. Do not label it evidence of grasp or task completion.

## Next bounded Unity work

1. **Run the existing native baseline on Quest.** Confirm two things separately: it starts with usable passthrough/hand controls, and capture → review → preload → independent placement → guide works. Use the exact tested commit/build and document device results. No new model is needed for this gate.
2. **One coherent UX controller.** Add a small `TutorialExperienceController` in native Presentation to orchestrate Home → Create/Follow. Reuse `CaptureReplaySession`, `NativeStorageFeature`, and `GuideController`; hide their diagnostic panels during normal operation. Keep Pairing/Settings available. Respect author vs learner credentials; no silent role escalation. Review can remain on desktop initially, with a clear “Ready for review / reviewed / ready to follow” state in the headset.
3. **Port save-zone authoring as a pure C# component.** Choose two stable visible palm positions once before capture; convert raw tracking-space positions after workspace registration, then persist workspace-local metadata. Reuse it across takes. Require a valid endpoint hold, then a deliberate return; trim pose and narration together. Clear dwell on missing tracking, pauses or origin changes. Keep the last saved take when replacement is discarded. Reset the zone only by explicit action or a new tutorial. Use a versioned authoring-metadata extension and TS/C# parity fixtures; never silently add fields to strict wire parsers.
4. **Pair the presentation with the native guide.** Render both required hands, preserve the existing reducer as progression authority, show a short ahead-of-learner cue and the actual tolerance zones. Add Watch / Your turn / Check result states. Cosmetic smoothing must never manufacture tracking validity or pass gates.
5. **Finish richer guidance only after this transfer works.** Reference photos, native narration and task-specific outcome inspection follow. Continuous object localization and deformable-object retargeting are separate projects; the current image-advice PR does not implement them.

## Import boundary

The local `trail.tutorial.prototype.v3` file is not the native recording contract. It has nullable individual joints, browser clocks, per-recording audio/photos, two-point placement and an optional `save_position` field. Native recording/sidecar schemas require different limits, validity, calibration, provenance and hashes. If old browser demonstrations are carried over, build a tested explicit converter that labels them external recordings or rejects unsupported data. Do not invent native sensor timestamps, provider evidence, a third calibration mark or fourth-point error. Do not copy local prototype JSON into native cache as “ready.”

The immediate integration should port behavior and tests into Unity, keeping this local page for quick UX experiments. Rebuilding networking/storage/progression in a second native stack would discard the strongest work already merged.
